Part 1: For modders

Fix what an evaluation found

Do this with an agent

By Richard Bejtlich, Richard Presents Starfield Essentials on YouTube

More Starfield tools and references are on the Richard Presents Development Hub.

Summary

When sf-mod-check check, release or triage reports a problem in a plugin, you find the record, fix it in xEdit or the Creation Kit (or rebuild it from code), and run the same check again until it is clean. No PMT tool edits a plugin. If the mod belongs to someone else, ask permission before you share a fix, and credit the author.

What you need

  • sf-mod-check 0.17.0, installed as in Getting started. It needs the game's Data folder for masters. The Steam default path is found by itself. For Game Pass, add --data "<drive>:\XboxGames\Starfield\Content\Data".
  • A tool that can edit the plugin. That is xEdit or the Creation Kit (CK) for most authors. Code builders use BuildKit and sf-mod-build instead. See the other free tools for links.
  • Vortex or MO2. Vortex deploys into the Data folder, so the checks work as they are. For a plugin that sits in a Vortex staging folder, add --data pointing at the real Data folder. For Mod Organizer 2 (MO2), give the plugin path inside mods\, add --data for the real Data folder, and add --masters-dir for each master mod's folder. (check doesn't take --mo2. conflict, patch and find do.)
  • A backup. Copy the plugin before you change it. The tools only read, so any damage would come from your editor.

Steps

1. Run the check

check tests a single plugin for structure, links, conditions, dialogue, scenes, deleted records and missing assets. Each line is an ERROR, a WARNING or a HINT, and the run ends with a RESULT: line.

Command Prompt
sf-mod-check check MyMod.esm

If you have a release zip, release checks the whole package. Its lines are PROBLEM, REVIEW, WARNING, NOTE and ACCEPTED.

Command Prompt
sf-mod-check release MyMod-1.0.0.zip

If the plugin came from someone else and you only want to know where to start reading, use triage. Its findings are NOTE and LOOK, never a verdict.

Command Prompt
sf-mod-check triage SomeMod-1.2.0.zip

Since sf-mod-check 0.17.0 (released 2026-11-24), triage shows every changed field of each official record the mod overrides, so you can see exactly what to fix. Very large records are cut at 200 rows, with a note that says how much was left out. The rows "same entries, other order" and "same English text, translations dropped" are often harmless, so fix the other rows first.

2. Find the record

Each finding names a record or a file. To read the record without opening an editor, run sf-mod-check find <EditorID or FormKey> --plugin MyMod.esm (with --masters-dir <folder> for each master that isn't in the plugin's folder or the game's Data folder). It prints the record's fields, including each condition on its own line. To edit it, open the plugin in xEdit or the CK and search for the Editor ID or FormID in the finding. Link the finding to its cause before you change anything. A link to a record that doesn't exist, for example, usually means a master is missing or a record was deleted.

3. Check what you can't see by eye

If you rebuild a plugin with Mutagen, gap finds data that Mutagen 0.54.4 loses when it writes a plugin. It is the same test as the mutagen-gap rule in release.

Command Prompt
sf-mod-check gap MyMod.esm

To see what an update of someone's mod changed, compare the old and new files.

Command Prompt
sf-mod-check diff SomeMod-1.1.0.zip SomeMod-1.2.0.zip

4. Fix it

Fix the record in xEdit or the CK. Code builders change the builder and rebuild:

Command Prompt
sf-mod-build build

Match how the game's own records and their siblings do it. Don't copy the quirks of the broken mod.

5. Run the same check again

Run exactly the command from step 1. Stop when it is clean. A different command can pass while the first one still fails.

Example

Say sf-mod-check check MyMod.esm reports a link to a record that doesn't exist. Open the record in xEdit, look at the field the finding names, and see that it points at a FormID from a master you removed. Point it at the right record, or remove the link. Save the plugin, run sf-mod-check check MyMod.esm again, and read the new RESULT: line.

Reading the results

Exit codecheckreleasediff
0No errors.OK.No differences.
1Errors found.FAIL.Differences found.
2The tool could not check.The tool could not check.Bad input.
  • ERROR and PROBLEM mean something is broken. Fix these first.
  • WARNING and REVIEW mean look at this and decide.
  • HINT and NOTE are information.
  • ACCEPTED marks a finding you chose to accept with --accept.
  • Triage uses only NOTE and LOOK. Treat it as where to start reading.

When PMT isn't enough

By design

No PMT tool edits a plugin. Cleaning ITMs, undeleting records and renumbering are xEdit or CK jobs, and so is applying any fix. PMT finds the problem and checks your result.

Note

Match how the game's own records and their sibling records do it, not the broken mod's quirks.

Warning

If the mod belongs to someone else, ask the author before you share a fixed version, and credit them. A fix for your own game is yours. A fix other people download needs permission. See Extend another author's mod for how to keep a permission record.

For CK and xEdit authors

You fix the plugin by hand, so PMT is your second pair of eyes. Run check before you save, again after, and release on the zip. Every finding names a record you can search for in xEdit or the CK.

For code builders

Fix the builder, not the plugin. Rebuild with sf-mod-build build, then run check and gap on the new plugin. Keep ids.lock.json with your builder so FormIDs stay stable between builds.
