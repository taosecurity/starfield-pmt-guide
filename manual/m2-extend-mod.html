Part 1: For modders

Extend another author's mod

Do this with an agent

By Richard Bejtlich, Richard Presents Starfield Essentials on YouTube

More Starfield tools and references are on the Richard Presents Development Hub.

Summary

You can add new content to another author's mod with an add-on plugin that uses the original as a master and adds your own records, and permission comes first. PMT then checks the add-on against the original build. BuildKit's README has a worked add-on example, and this page puts it together with the checks.

What you need

  • Permission from the original author. Read the mod's permissions on its page, ask the author, and keep their reply. Don't start building before you have it.
  • The original mod, installed. Your add-on needs the master plugin and, if it has one, the master's BA2 archive.
  • sf-mod-check 0.25.0, sf-cut-check 0.2.0, and for code builders sf-mod-build 0.5.1 and BuildKit 0.6.1. Install them as in Getting started.
  • Your setup. Steam is the default. sf-mod-build builds on Steam only, because the Creation Kit (CK) tools exist only there. Under Vortex, the master's folder is its staging folder. Under Mod Organizer 2 (MO2), it is the master mod's folder inside mods\.
  • A backup of your project folder and of your load order.

Steps

1. Ask first

Read what the author allows. If the page is silent, ask. Keep the reply (a screenshot or a saved message) where you keep your project. Credit the author in your README. Permission records are yours to keep. PMT doesn't track them.

2. Plan an add-on, not an edit

Make a new plugin that lists the original as a master and adds new records. Don't change the original's records. The add-on then works with future updates of the original and doesn't conflict with it. Give your records your own prefix. Use plain file names with no spaces.

As an example, take a spawner mod by another author. You want to add new NPC types that it can spawn. Your add-on adds the NPC records and any records they need, and leaves the spawner's records alone.

If the add-on will talk to one of the other author's NPCs or quests, read their conversations first. Since sf-mod-check 0.24.0 (released 2026-11-26), scenes prints an NPC's or a quest's conversations as a tree, with one section per scene, what the NPC says, and a table of the player's choices with where each one leads. It finds the talk menu by itself, and it changes nothing.

Command Prompt
sf-mod-check scenes OM_Quest --plugin OtherMod.esm --masters-dir <folder of OtherMod>

Give it the EditorID of an NPC or a quest. Read the tree before you decide where your lines fit, so your add-on joins the conversation instead of breaking it.

3. Make the plugin

If you use the CK, load the original as a master, add your records and save your own plugin. Don't edit the original's records.

Code builders do the same in a builder:

  • Open the master with GameData. Pass the other author's folder as an extra folder, which GameData searches before Data, so the build works without installing their mod. Open Starfield.esm, then their plugin: game.Open("OtherMod.esm") opens it read-only, and the master's own masters open first.
  • Look up their records with game.Get<IMiscItemGetter>("OM_Widget") and point your own records at them with .ToLink(). Get stops the build with a message such as no record OM_Widget in ... if their EditorID is missing, for example after they rename it. Nothing of theirs is copied or changed.
  • Call IdLock.Apply(mod, "ids.lock.json") so your records keep stable FormIDs from one build to the next. Commit ids.lock.json with the builder.
  • Write the plugin with BuildKit. It runs the gap check after writing.
  • You don't list the master by hand. Their plugin becomes a master of yours only because your records point into it. Players need both mods, with yours loaded after theirs.
  • Pass new WriteOptions { GapCheckMastersDir = @"<folder of OtherMod>" } when you write, so the gap check finds their plugin. IdLock locks the FormIDs of your own records only.
  • The whole example, "An add-on for another author's mod", is in BuildKit's README, section "More examples". The 0.6.0 README dropped that section by mistake, and BuildKit version 0.6.1 brought it back under the same headings.

4. Build with the master's folder

Your sfmod.json can list extra plugins your builder writes in parts. Since sf-mod-build version 0.5.0, each part gets its own zip, <ModName>-<Part>-<version>.zip, next to the main zip, and its release check gets the build's dist folder as a master folder, since its master plugin is in the main zip. See Release a mod for what that means for your upload.

Both build and check take --masters-dir for the master's folder, once per folder, and pass it to the release check, so the add-on is checked against the build you just made.

Command Prompt
sf-mod-build build --masters-dir <folder of OtherMod>
Command Prompt
sf-mod-build check --masters-dir <folder of OtherMod>

5. Check the add-on

Check the plugin, giving the folder that holds the master. check with --masters-dir also reads your plugin's own archive (MyMod - Main.ba2) next to the plugin, so your own scripts count as found. This needs sf-mod-check 0.16.2 or newer.

Command Prompt
sf-mod-check check MyMod.esm --masters-dir <folder of OtherMod>

Run the gap check with the same folder.

Command Prompt
sf-mod-check gap MyMod.esm --masters-dir <folder of OtherMod>

Check the zip. --master-archive counts the master mod's archive files as present, so your add-on isn't flagged for assets that live in the original. Give the archive's full path, not only its name.

Command Prompt
sf-mod-check release MyMod-0.1.0.zip --masters-dir <folder of OtherMod> --master-archive "<folder of OtherMod>\OtherMod - Main.ba2"

If your add-on adds scenes of its own, run scenes on its quest too. It lists broken jumps, choices with no way out and stages that nothing sets or reads (see Build a quest mod).

Command Prompt
sf-mod-check scenes MyQuest --plugin MyMod.esm --masters-dir <folder of OtherMod>

Last, look for records your add-on adds but never uses. scan --plugin reports only your own records.

Command Prompt
sf-cut-check scan --plugin MyMod.esm --masters-dir <folder of OtherMod>

Reading the results

  • check and release. Exit 0 means no errors or OK. Exit 1 means errors or FAIL. Exit 2 means the tool could not check. The last line of check is RESULT:.
  • gap. It finds data Mutagen 0.54.4 loses when it writes a plugin. Fix every ERROR.
  • sf-cut-check scan --plugin. It ends with a RESULT: line. Exit 1 means it found Orphaned or Unreferenced records. Read these as "nothing in the plugins uses it". They aren't proof, because scripts aren't read. A record that only a script fetches can look unused.
  • Missing master. Exit 2 from sf-cut-check can mean a missing master. Check the --masters-dir path.

When PMT isn't enough

By design

Permission records are yours to keep. PMT doesn't ask for them, store them or check them. Without the author's reply, don't release the add-on.

Note

Design box. Prefer adding over changing. Log with a mod prefix and a "Show Debug Messages (PC only)" switch, and see Test and debug a mod. Use plain file names with no spaces. If you have several plugins, one project per plugin is the safe route for now.

For CK and xEdit authors

Load the original as a master in the CK or xEdit, add records of your own, and save under your own plugin name. Never edit the original's records in place. Then run check, gap and release with --masters-dir and --master-archive as shown above.

For code builders

Open the master with GameData, lock your IDs with IdLock.Apply, write with BuildKit, and build with sf-mod-build. Pass the master's folder to every check. If your builder writes more than one plugin, list the others in parts, and sf-mod-build writes one zip per plugin.
