Part 1: For players

How PMT compares with other tools

Do this with an agent

By Richard Bejtlich, Richard Presents Starfield Essentials on YouTube

More Starfield tools and references are on the Richard Presents Development Hub.

Summary

This page compares PMT with Vortex, Mod Organizer 2, LOOT, xEdit and the in-game Creations menu, and says when to use PMT together with each one. PMT checks and reports, while those tools install, sort, edit and order your mods, so most players use PMT alongside them rather than instead of them. Every claim about another tool links to its source, checked on 2026-11-24.

The short answer

PMT doesn't replace the tools you already use. Vortex and Mod Organizer 2 (MO2) install and remove mods. LOOT sorts a load order. xEdit edits records. The in-game Creations menu installs and orders Creations. PMT checks what those tools produced, explains problems in plain words, checks saves and logs, and builds mods from code. It never installs, sorts from scratch, edits another author's plugin or uploads.

Note

Starfield reads Plugins.txt itself when it starts, and the game rewrites that file when it launches and when you move a Creation in the Creations menu. See Starfield Load Order Facts for the tests behind this. Some older xEdit documentation says the game doesn't read Plugins.txt. That is out of date.

What each tool does best

Vortex

Vortex is the Nexus Mods mod manager. It installs, enables and removes mods, and it deploys them into the real Data folder, which is why PMT tools work on a Vortex setup as they are. Its license is GPL-3.0 (repository). We read the v2.11.0 source on 2026-11-24 and didn't run it, so the points below say what the code does.

  • Where the Starfield support lives. The old vortex-games repository was archived on 2026-05-20 (vortex-games). Vortex now keeps a small Starfield game stub in its own repository (extensions/games/game-starfield), and the plugin handling for Starfield is in Vortex's own plugin management code (gamebryo_plugin_management/util/gameSupport.ts, lines 164 to 192).
  • Plugin management is off for Starfield by default. Vortex turns plugin management on by default for other Bethesda games but not for Starfield (gameSupport.ts, lines 421 to 424). Sorting, rules and plugin warnings all wait until you turn it on for your profile.
  • Sorting and rules, once it is on. Vortex sorts with LOOT's library (libloot 0.29.3, per its CHANGELOG.md), downloads LOOT's masterlist from the v0.29 branch (util/masterlist.ts, lines 9 to 16), and lets you add your own load-after rules and groups (actions/userlist.ts, lines 3 to 36).
  • Plugin warnings. It registers checks for missing masters, a blueprint plugin used as a master (Starfield only), unfulfilled rules, a bad userlist, missing groups and too many plugins (gamebryo_plugin_management/index.ts, lines 416 to 446 and 797 to 900). It reads plugin headers only, so it doesn't check conditions, links or assets, and its conflict view compares installed files, not records.
  • Saves, logs and updates. Its save game extension has a Starfield entry that is commented out (extensions/gamebryo-savegame-management/src/util/gameSupport.ts, lines 82 to 89). It shows its own logs and can pack them into a support bundle (Help, then Create support bundle, in the 2.11.0 notes). Its changelog updates Starfield's official plugin list for new DLC, but nothing checks your mods against a game update.
  • Before install. The mod report and the content column work on a mod's installed files (extensions/mod-report/src/index.ts, lines 85 and 86), so they describe a mod after you install it.
  • Agent docs. The repository has an AGENTS.md, but it tells an agent how to change and test Vortex's code, not how to use Vortex to manage mods.
  • Platforms. The v2.11.0 release has only a Windows installer. The repository has Linux build notes, and its own Flatpak page says that package is broken (docs/packaging/flatpak.md, lines 6 and 7).

Mod Organizer 2

MO2 keeps every mod in its own folder and shows the game a virtual Data folder, so your real Data folder stays clean. MO2 also gives the game its own copy of Plugins.txt, unless StarfieldCustom.ini has sTestFile lines, which turn MO2's plugin management off (Starfield Load Order Facts). Version 2.5.2 added Starfield Creation support, medium plugin support, save parsing for saves up to version 139 (it lists a save's missing plugins), Starfield archive packing, and LOOT sorting turned on by default through libloot 0.23.0 (2.5.2 release notes). MO2 2.5.2 sorts with libloot 0.23.0, which is older than LOOT 0.24.0's blueprint master support (LOOT changelog), so its built-in sorting may not know the newer Starfield rules, and running LOOT itself avoids that. The 2.5.3 betas build against libloot 0.29.4 and the v0.29 masterlist, and add their own blueprint plugin handling. That comes from the source code, and we haven't tried it in a run.

What the chart's other MO2 cells rest on, from the source of both 2.5.2 and beta 12 (read on 2026-11-24, not run):

  • Rules. MO2 keeps no rules or groups of its own. Its Sort button runs lootcli, which loads LOOT's masterlist and then your LOOT userlist.yaml from LOOT's own folder (lootcli/src/lootthread.cpp, lines 806 to 810 in the beta). A rule you want goes into LOOT's userlist.
  • Patches. Nothing in MO2 writes a plugin. Its "Create empty mod" action and its Overwrite folder hold the output of patch tools you run from MO2.
  • Before install. The Starfield data checker knows the folder names and file types a Starfield mod uses (starfieldmoddatachecker.h, lines 14 to 31, in modorganizer-game_bethesda), and the installers use it to judge an archive's layout. Nothing reads the plugins inside.
  • Logs. MO2 writes mo_interface.log into the logs folder of the instance and shows it in its log pane (modorganizer/src/shared/appconfig.inc, lines 10 and 14; loglist.cpp, lines 239 to 262). Its one log-reading plugin, the script extender plugin checker, has no Starfield entry.
  • Updates. MO2 checks for new versions of itself and of Nexus mods (selfupdater.cpp). Its Starfield problem checks are about plugin files, not about a game update (gamestarfield.cpp, lines 440 to 455).
  • Agent docs. None of the ten MO2 repositories we listed on GitHub on 2026-11-24 has an AGENTS.md or similar file.

MO2 2.5.2 and the 2.5.3 betas

MO2 2.5.2 (2024-08-04) is the last stable release. Newer builds, the 2.5.3 betas, are shared on the MO2 Discord. Beta 12 was released on 2026-05-23. The Discord isn't a public source, so the points below come from the upstream source code in the modorganizer-game_bethesda repository (where the Starfield support now lives), the modorganizer repository and the MO2 vcpkg registry. We read the beta 12 source on 2026-11-24 and did not run it, so we haven't tested what the game does with the differences.

What changed for Starfield between 2.5.2 and the betas:

  • Pinned official plugins, 8 to 12. MO2 pins Bethesda's own plugins at the top of the list and keeps them out of its plugins.txt. Version 2.5.2 pins eight. The betas pin twelve, including Shattered Space and Terran Armada, which 2.5.2 treats as ordinary plugins.
  • Blueprint plugins. Version 2.5.2 treats a BlueprintShips- file like any other plugin. The betas keep blueprint plugins in their own block after every other plugin, leave them out of plugins.txt, and warn about an invalid or unpaired blueprint file.
  • Starfield.ccc. Version 2.5.2 wrote its own Starfield.ccc and showed it to the game and to every program it started. The betas drop that and only read a Starfield.ccc that already exists.
  • Save version 153. Version 2.5.2 reads the plugin list of saves up to version 139 and likely misreads current saves (version 153). The betas read versions 140 and later. This comes from the source code and wasn't tried in a run.
  • LOOT 0.23.0 to 0.29.4. The sorting library inside MO2 (libloot) is 0.23.0 in 2.5.2 and 0.29.4 in the beta 12 source. A beta sort also shows the new order first and changes your load order only when you press Apply.
  • Creations shown by title. Version 2.5.2 listed each Creation plugin as its own entry. The betas show one entry per Creation, under its store title.

Two things stay the same in both versions. If StarfieldCustom.ini has sTestFile lines, MO2 maps nothing and turns its plugin management off. MO2 also has a command line that starts a program you have set up in MO2, inside its virtual Data folder: ModOrganizer.exe run -e "<configured executable name>", with -i <instance> and -p <profile> to pick the setup (modorganizer/src/commandline.cpp, lines 698 to 790 in the beta). It returns 0 when the program finished and 1 when it couldn't start it, never the program's own exit code. We haven't tried it.

If you use 2.5.2, check after you change your plugins that Shattered Space and Terran Armada are still ticked in MO2's plugin list. If you can get a beta or a later release, prefer it for Starfield.

LOOT

LOOT sorts a load order from its masterlist and your own userlist rules, checks for errors such as missing masters, and shows messages about plugins (loot.github.io). We read its changelog, its documentation and the Starfield masterlist on 2026-11-24 and didn't run LOOT.

  • Sorting history. LOOT 0.22.1 (2023-11-05) turned Starfield sorting off because it couldn't reliably tell when two Starfield plugins changed the same record. LOOT 0.23.0 (2024-07-10) fixed that check, turned sorting back on and added medium plugins. Later releases added blueprint masters (0.24.0) and warnings for BlueprintShips- and blueprint master mistakes (0.29.1, 2026-04-18) (changelog).
  • The Starfield masterlist. The masterlist has more than messages. On its v0.29 branch (last changed 2026-06-19) it has 13 groups plus the default group, and load-after rules for about 30 of its 59 plugin entries. Those rules mostly order Bethesda's own plugins and Creations. It has few entries for other authors' mods.
  • Patch days. When Starfield adds official plugins, a LOOT release adds them, for example 0.29.0 for Starfield 1.16.236.0. LOOT doesn't check your mods against an update, and we didn't check how quickly its releases follow a patch.
  • Conflicts and patches. LOOT's overlapping plugins filter shows which plugins change the same records, but not which records. It doesn't build patches.
  • Command line. LOOT is a desktop app, but it takes --game, --game-path, --loot-data-path and --auto-sort. With --auto-sort, it sorts, applies the order and quits, with no report (command line parameters).
  • Agent docs. The LOOT and libloot repositories have no AGENTS.md or similar file.

xEdit

xEdit (its Starfield mode is SF1Edit) is the standard tool for looking at and changing records by hand. It shows which plugin wins each record, cleans plugins, and can build patches by hand or by script (README). Its license is MPL-2.0 (repository). Since 4.1.5q, SF1Edit can edit and save .esp, light and medium plugins, with limits. It can't set or clear the light or medium flag (the notes say to do that in the Creation Kit), it won't save a plugin that has a blueprint master, and it doesn't create Update (Overlay) files yet (4.1.5s notes).

What the chart's xEdit cells rest on, from the 4.1.5s source and notes (read on 2026-11-24):

  • Sorting and rules. xEdit reads the active plugins from Plugins.txt (xEdit/xeInit.pas, lines 441 to 445) and doesn't sort them. Its Sort Masters command orders only the masters inside one plugin. Its ModGroups name plugins whose changes belong together, so it can hide overrides that add nothing new, but they aren't sort rules (ModGroups notes).
  • Patches. It ships Edit Scripts such as "Copy as override" and "Merge overrides into master", and a built-in Merged Patch whose notes name Starfield. None of the scripts is written for Starfield, and we didn't run them on Starfield. We also haven't tried saving a light or medium plugin in SF1Edit, or used its conflict view on Starfield: those points come from the notes and the source.
  • Checks. Its Check for Errors command is also in xDump.exe, the command-line reader that ships with xEdit (-check). We ran it on 4.1.5r hotfix 2 and 4.1.5s. xDump's exit code is 0 even when it fails, so a run counts as finished only when its error output ends with "All Done.".
  • Saves. xDump says it doesn't support Starfield saves.
  • Logs. xEdit writes its session log next to the program, named after the game and the tool, for example SF1Edit_log.txt (xEdit/xeInit.pas, line 1267; we haven't confirmed the exact name from a run). Its log analyzer reads only Oblivion's script profiler log and Skyrim's Papyrus log (xEdit/xeLogAnalyzerForm.pas, lines 739 to 750).
  • Agent docs. The repository at the 4.1.5s tag has no AGENTS.md or similar file.

The Creations menu

The Creations menu is built into the game. It installs Creations and lets you reorder them, with full masters first, then light masters, then other plugins, and it can block saving when two files share a name (Bethesda support: load order). It shows no record conflicts, and Bethesda's support page describes no other check on the files than that duplicate name warning. In our own play on 2026-11-24, the game warned when we loaded a save that used a Creation we had since removed. You can restore an order only if you saved it to the Load Order Archive earlier, which is tied to your Bethesda.net account (Bethesda support: Load Order Archive). Many Creations are free, and some cost Creation Credits. Creations are ordinary plugins in the same Data folder and the same Plugins.txt as your other mods (Starfield Load Order Facts). It is the only one of these tools on consoles.

PMT

PMT's strength is checking and explaining, and sf-load-order 0.3.0 can also sort. It tells you what is wrong in a load order, a plugin, a release zip, a save or a log, in plain words, with a RESULT: line and an exit code. It also builds mods from code. Every tool ships an AGENTS.md, so an AI agent can run it the way its author intended (see Agents and the other modding tools).

When to use PMT with them

  • LOOT or sort, then sf-load-order. Let LOOT sort, then run .\sf-load-order.cmd to check the result, and give it LOOT's masterlist with --loot-masterlist so its suggestions follow the same rules. Or run .\sf-load-order.cmd sort, which keeps your current order wherever the rules allow and writes files for you to apply. Pick LOOT when you want its own interface and its groups. Pick sort when you want your own rules and as few moves as possible. See Check and improve a load order.
  • Vortex or MO2, then PMT. Install and remove mods with your manager, then check with PMT. For Vortex, deploy and run sf-load-order on the Plugins.txt that Vortex writes. With our Vortex Modlist Backup fork (no release yet), use --vortex-profile <name> instead. For MO2, use --mo2 <instance> --profile <name>, on sf-load-order and also on sf-mod-check conflict, patch and find.
  • PMT, then xEdit. When sf-mod-check's conflict report lists records it can't patch, such as quest and dialogue records, fix those in xEdit. Any fix to a plugin is an xEdit or Creation Kit job. See Find conflicts and build a patch.
  • The Creations menu, then sf-load-order. Order your Creations in the menu, then run .\sf-load-order.cmd with no options to check the game's Plugins.txt. If it suggests changes, make them in the menu.
  • Before you install anything. Run sf-mod-check triage on the download. None of the other tools reads the plugins inside a mod before it is installed. See Evaluate a mod before you install it.

Note

When the Creations menu and a mod manager both reorder your plugins, the last tool to write Plugins.txt wins (Starfield Load Order Facts). Pick one place to set the order, and check it with sf-load-order after any change.

When PMT isn't enough

By design

PMT doesn't install mods or edit records, and sort never applies an order itself: it writes files and steps for you to follow. Use Vortex, MO2 or the Creations menu to install and apply an order, and xEdit or the Creation Kit to change records. PMT checks the result.

By design

PMT runs on a PC. Console players can use only the Creations menu. To check a Creation, install it on a PC and run PMT there.
