Part 1: For modders

Release a mod

Do this with an agent

By Richard Bejtlich, Richard Presents Starfield Essentials on YouTube

More Starfield tools and references are on the Richard Presents Development Hub.

Summary

Build the release zip, run sf-mod-check release with the basic or creations profile, confirm with sf-test-plan that the zip is the build you tested, and write a README that explains logging and credits. You upload to Nexus Mods yourself, and the Creation Kit does the Creations upload. After a game patch, sf-patch-day tells you whether your mod needs a rebuild.

What you need

  • sf-mod-check 0.17.0, sf-test-plan 0.4.0 and sf-patch-day 0.3.0, installed as in Getting started. Code builders add sf-mod-build 0.4.2.
  • A tested build. See Test and debug a mod. The tutorial mods PMTTutorialSecondWind and PMTTutorialCourier are examples. Their WALKTHROUGH.md files, in the guide repository's examples folder, record the release checks they ran.
  • Your setup. The release zip should have the plugin and its BA2 archives at the top level, so Vortex and MO2 install it as it is. Steam is the default for building. sf-mod-build builds on Steam only.
  • Permissions. If your mod uses another author's work, you need their permission on record and their credit in the README.

Steps

1. Build the release zip

Code builders build everything in one command, which compiles, makes the plugin, packs the archives, writes the zip and runs the check. It stops at the first failure.

Command Prompt
sf-mod-build build

Since 0.4.2, build shows the result of BuildKit's gap check without --verbose: its gap check: RESULT: ... line, its ERROR lines, or gap check: NOT RUN (...) when sf-mod-check wasn't found. Fix every ERROR. If you name a checker with --checker <exe>, it is given to the gap check too (0.15.0 or later).

To make the release check mandatory, run the check step with --require-check.

Command Prompt
sf-mod-build check --require-check

If you made the zip another way, go straight to step 2.

2. Run the release check

The basic profile checks the package for any release.

Command Prompt
sf-mod-check release MyMod-1.0.0.zip --profile basic

For a mod you plan to put on Creations, use the creations profile. It applies the rules for PC, Xbox and PlayStation.

Command Prompt
sf-mod-check release MyMod-1.0.0.zip --profile creations

If you build with sf-mod-build and "xbox": true, the files you upload (the plugin, the PC archive and its _xbox.ba2 twin) go into a folder named creations-out. Check that folder, not the PC zip, which has no Xbox archive. Without "xbox": true there is no creations-out folder, and the command stops with RESULT: CANNOT CHECK (creations-out: no such file) and exit 2. sf-mod-build build doesn't run this check itself, but with "xbox": true it ends by printing the command with your folder's full path:

Command Prompt
sf-mod-check release creations-out --profile creations

Each Creations rule means this, in plain words:

RuleWhat it means
creations-iniNo INI files in the package.
creations-sfseNo DLL or SFSE plugin files in the package.
creations-frameworkNo scripts that name an SFSE plugin framework.
creations-masterMasters are only Bethesda's, plus ones you vouch for with --creations-master.
creations-xboxEach PC texture archive needs a _xbox.ba2 twin.
creations-sizeThe package stays under the 2 GB cap.
creations-audioA warning for .wem and .bnk audio, which is silent on consoles when it is PC-only.
creations-debugA warning for Debug.Notification and MessageBox, which consoles ignore.

--tested <zip or BA2> names the zip, or one of the .ba2 archives, of the build you played. The release check then compares the build's plugins and scripts with that build: a script or plugin that differs, is missing now or is new is a REVIEW line, and one that matches is a NOTE. A tested file that can't be read is a PROBLEM. To accept a finding you decided to accept, use --accept rule:plugin:detail.

3. Confirm it is the build you tested

check-build says whether the zip you built has the same plugins and scripts as the zip you tested.

Command Prompt
sf-test-plan check-build MyMod.testplan.md --built MyMod-1.0.0.zip --tested MyMod-0.9.0.zip

4. Write the README

Say what the mod does, what it needs, how to install it and how to remove it. Then add:

  • A logging section. Say how to turn on Papyrus logging: add [Papyrus] with bEnableLogging=1, bEnableTrace=1 and bLoadDebugInformation=1 to StarfieldCustom.ini, and where the log goes (Documents\My Games\Starfield\Logs\Script\). A mod with scripts also tells players about its "Show Debug Messages (PC only)" switch. A records-only mod doesn't need either.
  • Credits and permissions. Name every author whose work you used, and say what permission you have.
  • One plugin per zip. Put at most one plugin in each zip. A second plugin gets its own zip, named like MyMod-Part-1.0.0.zip. Don't use "Optional" folders, because Vortex installs them as they are, so their plugins never load.

5. Upload

You upload to Nexus Mods yourself. For Creations, the Creation Kit does the upload. PMT never uploads anything. Read your page text, screenshots and version number again before you submit.

6. Keep it working after a game patch

drift tells you whether an update changed the master records, quest stages or script functions your mod relies on. Do init and snapshot once, when you release.

For the script functions and quest stages, drift needs sf-pex-tools 0.1.0. Unzip it into a folder named sf-pex-tools next to the sf-patch-day folder, or add --pex-tools <folder> to each drift command. Without it, init lists only the master records your plugin overrides. A mod that adds only its own records, like the tutorial mods, then gets a mods file with nothing to watch, and snapshot stops with exit 3 ("masters" is empty). With sf-pex-tools, init on the quest tutorial listed 21 functions that its scripts call in Starfield.esm, and snapshot and check ran (RESULT: no change, exit 0).

Command Prompt
.\sf-patch-day.cmd drift init MyMod.esm -o mods.json
Command Prompt
.\sf-patch-day.cmd drift snapshot --mods mods.json -o baseline.json

After a game update, run check.

Command Prompt
.\sf-patch-day.cmd drift check --mods mods.json --baseline baseline.json

For a mod that relies on a Creation you don't make, list that Creation in the mods file, because drift doesn't watch Creations by itself.

Reading the results

  • Release lines. PROBLEM means a defect you must fix. REVIEW and WARNING mean judge it. NOTE is information. ACCEPTED is a finding you chose to accept. Exit 0 is OK, exit 1 is FAIL, and exit 2 means the tool could not check.
  • check-build. Exit 0 means the same plugins and scripts. Exit 1 means the zips differ.
  • drift check levels. OK, NOTE, WARN, ACTION (rebuild) and SKIP. Exit 0 is no change, exit 1 means a change that is unused or a name to check, exit 2 means rebuild, and exit 3 means it could not read.
  • BA2 bytes vary. Compile times make BA2 bytes differ between builds, so judge by plugins and scripts, which is what check-build compares.

When PMT isn't enough

By design

PMT never uploads. Nexus Mods and Creations uploads are your own steps, and the Creation Kit does the Creations upload and makes the console audio.

Not in PMT yet

sf-mod-build makes one zip per project. For a mod with more than one plugin, use one project per plugin for now, or split the zip with your own script. A zip-per-plugin option is coming.

See the Coming next list

Not in PMT yet

PlayStation packaging isn't documented in PMT yet, and PMT has not been tested on PlayStation 5. PMT checks the Creations rules and makes the Xbox archives. For what a PlayStation 5 Creation needs, follow what the Creation Kit asks for during its upload.

See the Coming next list

Not in PMT yet

sf-patch-day doesn't watch the Creations you depend on, unless you list them in a drift mods file.

See the Coming next list

Warning

After a game update, never rerun snapshot --force instead of check. It replaces the baseline, so you lose the record of what changed.

For CK and xEdit authors

Make the zip by hand with the plugin and its archives at the top level, then run release on it. Use the CK for the Creations upload, and drift init MyMod.esm in your mod's own folder for patch-day upkeep.

For code builders

Let sf-mod-build build make the zip, and run its check step with --require-check so a failed release check stops the build. Keep the pinned Mutagen and BuildKit versions, and never compile with -release.
